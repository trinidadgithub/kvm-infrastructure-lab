## 5. P0: Makefile approval and scope audit (historical defect and fix)

**Historical P0 cause, corrected in Phase 2:** GNU Make executes separate recipe lines in separate shells unless explicitly joined. Before this correction, `tf-destroy`/`tf-destroy-auto` put `read; if declined then exit 0; fi` in one recipe shell, but `mkdir` and `terraform destroy` in **subsequent** recipe shells. Declining exited with success **only from the prompt shell**; Make continued to the next lines. `tf-destroy-auto` then passed `-auto-approve`, bypassing confirmation entirely. An EOF/noninteractive `read` did not establish approval either. The historical `docs/lab-plan.md` called those guards safe; that claim was false. Do not use older commits' legacy destroy recipes.

### Implemented Phase 2 operation controller

The initial generic `bin/confirm-operation -- <arbitrary command>` approach **failed adversarial review**: MAKE/MAKEFLAGS, SHELL, PATH-interpreter, ANSIBLE_DIR and PACKER_DIR overrides could invoke a stubbed destroy without a matching destroy authorization. Those observations came only from disposable stubs, not a live host. The generic helper was replaced by the reviewed, fixed-mapping controller. **Do not run protected operations on persistent resources merely because the stub suite passes; each requires a separately reviewed plan and operator approval.**

The [operation controller](OPERATION-CONTROLLER.md) maps a structured operation and reviewed environment to a fixed root and exact command internally. It does not accept arbitrary execution arguments or shell fragments. A Git-ignored `.local-tools.json` records absolute and canonical executable paths (including tfenv's versioned binary), and a per-checkout lock rejects overlapping controller processes. Make fixes its protected recipe shell/Python path, does not recurse for `up`, and passes only fixed operation/environment identifiers; it is a convenience entrypoint, not the approval authority. `tf-apply-auto`/`tf-destroy-auto` remain disabled. The **original Phase 2 commit** had no workstation tool manifest and validated only fixture behavior. Subsequently the operator-approved manifest was created Git-ignored with mode `0600`, `/usr/bin/python3 -I bin/operate validate-tools pty-regression` passed without executing configured tools, and the separately approved PTY bootstrap succeeded. This manifest and bootstrap approval do **not** authorize any later cleanup, recovery or persistent-environment operation.

## 7. State protection, recovery and troubleshooting

Each Terraform root's local state is authoritative for **its own** resources, not a backup of guest data or ZFS images. Confirm root path and target libvirt URI before any command; do not copy K3s state to Ubuntu or let two roots own the same libvirt object. Record `terraform state list` and a reviewed plan for the chosen root without printing sensitive state into logs. The legacy `state-backup` and `env-state-backup` commands create only local copies. Plan for an access-controlled **off-host** backup of state *and* independent backup/retention of guest overlays and their published backing images; protect all from Git and indiscriminate deletion. Backing-chain recovery requires the exact referenced image path and contents. Host snapshots are not a tested replacement for consistent guest backups.

For an operator-authorized backup, freeze concurrent Terraform writers, confirm the intended root with `make ENV=ubuntu-servers env-info`, then use `terraform -chdir=environments/ubuntu-servers state list` to inventory addresses. With `umask 077`, capture a dated `terraform -chdir=environments/ubuntu-servers state pull` into a **new** protected file outside the checkout and `kvmpool`; check it is nonempty and valid JSON, store a second copy off-host, and record the matching image/checksum and overlay backup point. For K3s, substitute `terraform/` and its own host-specific backup destination. Never display the full state on a shared terminal or commit it.
