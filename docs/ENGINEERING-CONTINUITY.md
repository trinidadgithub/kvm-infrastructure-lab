## 5. P0: Makefile approval and scope audit (historical defect and fix)

**Historical P0 cause, corrected in Phase 2:** GNU Make executes separate recipe lines in separate shells unless explicitly joined. Before this correction, `tf-destroy`/`tf-destroy-auto` put `read; if declined then exit 0; fi` in one recipe shell, but `mkdir` and `terraform destroy` in **subsequent** recipe shells. Declining exited with success **only from the prompt shell**; Make continued to the next lines. `tf-destroy-auto` then passed `-auto-approve`, bypassing confirmation entirely. An EOF/noninteractive `read` did not establish approval either. The historical `docs/lab-plan.md` called those guards safe; that claim was false. Do not use older commits' legacy destroy recipes.

| Target(s) | Historical pre-correction behavior | Phase 2 resolution or remaining limitation |
| --- | --- | --- |
| `tf-destroy`, `tf-destroy-auto` | **P0:** prompt isolated from destructive recipe; refusal did not stop Terraform. | `tf-destroy` invokes fixed-mapping controller with exact `destroy k3s-lab` authorization; `tf-destroy-auto` is disabled. Tested with stubs only. |
| `env-tf-destroy` | Prompt and destroy shared one shell, but omitted `ENV` silently selected K3s. | Explicit command-line `ENV` and controller token are required. Operator must still review a destroy plan and backup. |
| `up` | Auto-approved K3s apply and parallelizable Make prerequisites could run Ansible before apply finished. | Controller runs K3s preflight, separately approved apply, then separately approved Ansible configuration in order; no automatic rollback after partial success. |

| `tf-*`, `state-backup`, `ansible-site`, `check` | Legacy targets ignored `ENV`; e.g., `ENV=ubuntu-servers tf-destroy` still targeted K3s. | Legacy targets require `ENV=k3s-lab`; env targets require explicit selection. `check` still requires existing K3s pool/state and is not a bootstrap workflow. |

### Implemented Phase 2 operation controller

The initial generic `bin/confirm-operation -- <arbitrary command>` approach **failed adversarial review**: MAKE/MAKEFLAGS, SHELL, PATH-interpreter, ANSIBLE_DIR and PACKER_DIR overrides could invoke a stubbed destroy without a matching destroy authorization. Those observations came only from disposable stubs, not a live host. The generic helper was replaced by the reviewed, fixed-mapping controller. **Do not run protected operations on persistent resources merely because the stub suite passes; each requires a separately reviewed plan and operator approval.**

The [operation controller](OPERATION-CONTROLLER.md) maps a structured operation and reviewed environment to a fixed root and exact command internally. It does not accept arbitrary execution arguments or shell fragments. A Git-ignored `.local-tools.json` records absolute and canonical executable paths (including tfenv's versioned binary), and a per-checkout lock rejects overlapping controller processes. Make fixes its protected recipe shell/Python path, does not recurse for `up`, and passes only fixed operation/environment identifiers; it is a convenience entrypoint, not the approval authority. `tf-apply-auto`/`tf-destroy-auto` remain disabled. No workstation tool manifest was created on the real host in this phase, so protected operations fail closed until an operator reviews and supplies one. `/usr/bin/python3 -I bin/operate validate-tools ubuntu-servers` checks the manifest **without executing any configured tool**; its fixture-only behavior was tested, not a real workstation manifest.

**Stub-only results on 2026-11-02:** all 12 tests in `python3 -m unittest discover -s tests -p 'test_make_safety.py' -v` passed in disposable copies with absolute-path Terraform, virsh, Ansible and Packer stubs. Tests cover the previously demonstrated overrides, direct command injection, denial/EOF/SIGINT, exact positive operation scope, fixed binary/symlink resolution, read-only manifest validation, child exit status/lock release, unknown/cross-root/UUID-mismatched VMs, sequential `up` with a failing later step and concurrent Make processes. A directly invoked controller returned stubbed child exit 42; GNU Make returned its normal error status 2 while printing the child status. No real infrastructure commands were run. A passing stub suite is not proof of provider behavior or an approved infrastructure change.

Remaining limitations: this is an **operational safety** control, not a security boundary against a user able to change the repository, manifest, execution account or installed binaries. An in-place binary replacement, direct Terraform/virsh invocation or a different checkout is not stopped by the per-checkout lock; Terraform state locking remains essential. Confirmation is not saved-plan review, and interruption **after** a command starts cannot roll it back. Apply/destroy require existing state, so new environment bootstrap needs a separately approved lifecycle procedure (see the controller runbook). `up` still needs existing K3s state/pool; local state backups are not off-host backups. Snapshot uses local `qemu:///system`, not arbitrary provider URIs, and is not a guest-consistent backup. Consult the linked runbook before approving further operational use. No Terraform module, state, image or Ansible configuration was changed in this phase.

Outside Make, `bin/destroy-vm` calls `virsh undefine --remove-all-storage`; it bypasses Terraform state ownership and must never be used on state-managed K3s or Ubuntu domains. `bin/create-vm` creates manually managed domains on the libvirt default network; do not mix those with Terraform-managed names/volumes.

## 6. PTY provider issue and disposition

**Observed by operator:** initial Terraform apply created both Ubuntu domains successfully but returned an inconsistent result when the planned `devices.consoles[*].source.pty.path` was `""` and libvirt readback contained runtime `/dev/pts/21` or `/dev/pts/22`. Terraform marked the domains tainted. After confirming domain presence, successful guest/cloud-init/SSH/agent operation and state ownership, the operator used `terraform untaint`; subsequent plans returned no changes. This is a **historical verified recovery reported by the operator, not a general untaint instruction**. Never untaint an unexplained partial resource or repeat this procedure without checking domain XML, backing storage, state and plan.

**Repository/schema verified:** `terraform/modules/compute/main.tf` retains `ignore_changes = [devices]`. The locally installed libvirt 0.9.9 provider schema marks `devices.consoles` optional, but `source.pty.path` **required whenever `source.pty` is configured**; omitting just that field fails schema validation. Its [v0.9.9 domain resource](https://github.com/dmacvicar/terraform-provider-libvirt/blob/v0.9.9/internal/provider/domain_resource.go) converts libvirt XML into state after create/read. Upstream [console/serial default report #1332](https://github.com/dmacvicar/terraform-provider-libvirt/issues/1332) describes libvirt-populated PTY paths. [Console inconsistency report #1294](https://github.com/dmacvicar/terraform-provider-libvirt/issues/1294) concerns other console fields and versions; it does not prove a fix here. Libvirt's ability to omit a PTY path in XML does not override this provider's schema.

**Workaround not yet validated on creation:** in committed `4602614`, `enable_serial_console = false` for Ubuntu makes `consoles = []`; default `true` keeps the K3s caller's existing explicit PTY behavior. A guest-agent channel is separately optional (`false` by default, `true` for Ubuntu). It is not yet known whether libvirt adds a default console and whether provider readback tolerates it on first create. Existing Ubuntu VMs predate the setting. `ignore_changes = [devices]` may conceal runtime changes on later plans and must not be removed without a replacement-impact analysis. No stable, useful PTY serial-console configuration has yet been demonstrated with this provider; alternative source types need schema review **and** isolated creation/reconciliation testing, not edits to persistent domains.

## 7. State protection, recovery and troubleshooting

Each Terraform root's local state is authoritative for **its own** resources, not a backup of guest data or ZFS images. Confirm root path and target libvirt URI before any command; do not copy K3s state to Ubuntu or let two roots own the same libvirt object. Record `terraform state list` and a reviewed plan for the chosen root without printing sensitive state into logs. The legacy `state-backup` and `env-state-backup` commands create only local copies. Plan for an access-controlled **off-host** backup of state *and* independent backup/retention of guest overlays and their published backing images; protect all from Git and indiscriminate deletion. Backing-chain recovery requires the exact referenced image path and contents. Host snapshots are not a tested replacement for consistent guest backups.

For an operator-authorized backup, freeze concurrent Terraform writers, confirm the intended root with `make ENV=ubuntu-servers env-info`, then use `terraform -chdir=environments/ubuntu-servers state list` to inventory addresses. With `umask 077`, capture a dated `terraform -chdir=environments/ubuntu-servers state pull` into a **new** protected file outside the checkout and `kvmpool`; check it is nonempty and valid JSON, store a second copy off-host, and record the matching image/checksum and overlay backup point. For K3s, substitute `terraform/` and its own host-specific backup destination. Never display the full state on a shared terminal or commit it. Timestamp-only local `cp` targets in Make are convenience copies, not a complete recovery strategy.

**When state is missing/corrupt or Terraform proposes unexpected replacement:** freeze applies/destroys, preserve current state and disks, identify the correct root/host, compare resource addresses and UUIDs with live read-only libvirt XML, then locate the most recent verified backup. Review restore/import strategy and permissions with the operator **before** touching state; never initialize empty state against existing domains or remove resources to silence drift. After an explicitly approved restore, recheck state ownership and a fresh plan. A no-op plan may still mask device drift; compare domain XML, disks and guest health separately. If a plan marks a known-good domain tainted, diagnose before untainting. This assessment did not test restore.

**Troubleshooting pointers:** an image checksum/backing-chain failure → compare expected hash and `qemu-img info --backing-chain` without modifying the image; guest SSH/bootstrap failure → inspect the selected inventory, DHCP lease, cloud-init status and guest console/agent availability; ISO/overlay access failure → inspect pool directory traversal, QEMU user/group and AppArmor denials without disabling confinement; PTY inconsistency → compare plan/state and domain XML, pause further operations. Ansible failures → check selected inventory root, role path, syntax and the specific task before applying again. Do not conflate *declared* `vm_ips` with observed addresses.
