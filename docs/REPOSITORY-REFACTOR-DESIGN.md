# Repository refactor design: independent KVM environments

## Scope and evidence

This is a design and migration plan, not an implementation. No infrastructure changes are required to adopt this document. **Verified** statements below describe the checked-in implementation; **proposed** statements describe future work. Host runtime, live libvirt XML, actual state contents, Packer build results, and the contents of the machine-local `terraform/terraform.tfvars` were **not verified**. Earlier planning documents (`docs/implementation-plan.md` and `docs/review-findings.md`) describe older versions of the repository; use current source files, not their historical findings, as the migration baseline.

## 1. Current architecture assessment

| Layer | Verified implementation | Consequence |
| --- | --- | --- |
| Terraform | One root at `terraform/`, local backend by default, `dmacvicar/libvirt ~> 0.9`, `qemu:///system` (`versions.tf`, `provider.tf`). Root declares `libvirt_pool.lab`, `libvirt_network.lab`, and `module.compute`. | This configuration is intended to manage the entire K3s lab in one state; actual state contents need host verification. Moving files or changing the root alone does not change resource addresses, but moving/copying state incorrectly can orphan or duplicate ownership. |
| VM lifecycle | `modules/compute/main.tf` uses `for_each` on a four-VM map, creates a qcow2 overlay per VM with `backing_store.path`, a cloud-init disk, and a running domain. Domain disks use file paths. `ignore_changes = [devices]` is present. | The backing image must remain available and unchanged for the life of dependent disks. Device drift is deliberately hidden from plans, so validate live attachments separately. |
| Networking | Root `network.tf` owns `lab-net`, bridge `virbr1`, NAT, `192.168.123.1/24`, DHCP reservations for jumpbox/master/two workers, and `lab.internal`. The module accepts one network name and one MAC per VM. | Reservations and compute are defined separately and must agree. An independently managed environment needs a distinct network or an explicitly external network owner. |
| Storage | Root `pool.tf` owns directory pool `lab` at `/var/lib/libvirt/images/lab` with numeric group `64055`. `variables.tf` defaults the backing image to `/var/lib/libvirt/images/lab/base/ubuntu-24.04-server-cloudimg-amd64.img`. | Pool, image and permissions are host-specific. The base image is referenced by path, not produced by Terraform. Cloud-init disks have no explicit pool argument in the checked-in module. |
| Image build | `packer/ubuntu-24.04.pkr.hcl` downloads a pinned Ubuntu 24.04 cloud image, builds qcow2 into `packer/output-ubuntu2404`, names the build VM `ubuntu-24.04-lab-base`, and installs baseline tools. `create-seed.sh` generates `packer/seed.iso` using the operator's public key. | No checked-in publication/copy step connects Packer output to Terraform's default image path. The `variables.pkr.hcl` inputs for key, image URL and checksum are declared but not referenced by the builder. Build success and actual output filename have not been verified. |
| Guest init | Root renders shared templates in `cloud-init/` for every VM. Template sets hostname, `iid-${hostname}`, SSH key, qemu guest agent, baseline packages, and lab sysctls including IPv4 forwarding. | Generic provisioning inherits lab tuning and one workstation key. A stable instance ID may prevent cloud-init from re-running as expected on replacement/reuse. |
| Configuration | `ansible/inventories/terraform.py` emits static JSON for the four hosts/IPs, with a key-path fallback; it does **not** read Terraform. `playbooks/site.yaml` runs jumpbox, server, then agents. `group_vars/all.yaml` includes `k3s_version`. | Inventory and DHCP must be updated together; running the existing site play against generic VMs is inappropriate. K3s token passes from server to agents via Ansible hostvars. |
| Operations | `Makefile` hardcodes `TF_DIR=terraform`, the `lab` pool and cloud-init `TMPDIR`, checks for an existing state and pool even before `up`, backs up only the old state path, and snapshots *all* running libvirt VMs. `bin/create-vm` separately creates unmanaged VMs on libvirt `default` with a fixed base path and `~/workspace/lab`; `bin/destroy-vm` directly undefines domains and storage. | Neither Make nor the manual scripts are safe environment selectors. Do not use direct `virsh` destruction for Terraform-managed domains. |

The image/dependency chain is: Packer build (external artifact) → operator publishes immutable backing image → pool and network (Terraform root) → per-VM overlay and cloud-init disk → domain → Ansible inventory and playbooks. Terraform references the image path but does not create or validate that artifact's provenance. No backend or shared-resource ownership contract currently spans multiple roots.

## 2. Separation-of-concerns violations

* `terraform/locals.tf` hardcodes the K3s VM names, capacities, MACs and a home-directory SSH-key search. `network.tf` separately hardcodes the same identities and fixed IPs; `ansible/inventories/terraform.py` repeats their names and IPs a third time.
* Generic `cloud-init/user-data.tftpl` embeds `/etc/sysctl.d/90-lab.conf` network forwarding and socket tuning. Keep K3s-specific tuning in K3s guest configuration, not in the generic Ubuntu baseline.
* `ansible/group_vars/all.yaml` puts `k3s_version` in variables for every host, and the default site play is entirely K3s/jumpbox-oriented. `jumpbox.yaml` installs kubectl/k9s/helm; it is not a generic Ubuntu baseline. The K3s role itself is already workload-specific.
* Pool path, bridge name, group ID, network subnet, static leases, key paths, `TMPDIR`, Packer seed location and manual VM scripts assume the first workstation. `README.md` also names an old `~/workspace/lab` source location; `docs/lab-plan.md` documents that workstation's resource ceiling, not a universal limit.
* `.gitignore` only covers state under `terraform/`; new environment states and backups need ignore rules. The existing `terraform/.terraform.lock.hcl` pins only the old root's provider selection; new roots need their own reviewed lock files.

## 3. Target structure and immediate scope

Use two small Terraform roots and retain the existing compute module location initially. Moving a module directory adds source-path churn without creating useful isolation. Introduce optional network/pool modules **only if a second root actually needs to create the same kind of resource**; a small root-owned pool or network block is simpler than a wrapper module used once.

```text
packer/                         # Ubuntu image build and seed; later image publication instructions
cloud-init/                     # shared minimal Ubuntu user-/meta-data templates
terraform/modules/compute/      # shared VM, overlay, cloud-init resources (existing module)
environments/
  k3s-lab/                     # migrated existing root, owns its current pool and network
  ubuntu-servers/              # second workstation: two data-driven Ubuntu 24.04 VMs
ansible/
  roles/ubuntu_base/            # only if common configuration merits a role
  roles/k3s/                    # existing workload role
  playbooks/ubuntu-servers.yaml # generic, no Kubernetes
  playbooks/site.yaml           # preserve K3s play order
  inventories/                 # environment-specific inventory or generator inputs
Makefile                        # environment-selected Terraform operations
bin/                            # manual helpers documented as separate from Terraform
docs/
```

If the old workstation is still actively managed, stage the new `ubuntu-servers` root on the second workstation first and leave `terraform/` intact until the K3s migration is independently validated. On a single workstation, use disjoint libvirt names, MACs, subnets/bridges, pool paths and domains across roots. Use environment-specific names such as `ubuntu-servers-net`/`ubuntu-servers-pool`; do not use Terraform workspaces to disguise a shared resource graph. Two VMs should be examples in `ubuntu-servers` input data, not hard-coded into the module.

## 4. Terraform interfaces (proposed)

Keep the module's existing resource addresses (`module.compute.libvirt_volume.vm_disk["…"]`, `module.compute.libvirt_cloudinit_disk.commoninit["…"]`, `module.compute.libvirt_domain.vm["…"]`) during K3s migration. The following is a **target interface**, not current Terraform code:

| Interface | Inputs | Outputs / responsibility |
| --- | --- | --- |
| `compute` | `vms = map(object({ hostname = string, memory_mib = number, vcpu = number, disk_bytes = number, mac = string }))`; `pool_name`, `network_name`, `base_image_path`; `cloudinit_data = map(object({ user_data = string, meta_data = string }))` keyed by VM map keys. | VM names/UUIDs and (if verified with this provider) domain interface data. Keep domain name as map key; hostname is guest configuration. The one-network-per-module interface already covers both roots; add per-VM network assignment only if mixed-network VMs are required. |
| `network` (conditional) | unique name, bridge, NAT mode, gateway/netmask, DHCP range, reservations (derived from the same VM input map where possible), optional DNS domain. | network name; manages a network **only in its owning root**. For the initial refactor, keep `libvirt_network.lab` directly in K3s root, and define the new root's network directly until extraction is justified. |
| `storage` (conditional) | unique pool name, absolute directory path, permissions appropriate to that host. | pool name; manages a pool **only in its owning root**. Base image is a separately published, read-only host artifact, not a VM overlay and not owned by multiple states. |

Root inputs should be explicit: `libvirt_uri` (default `qemu:///system`), `pool_name`, `pool_path`, `network` configuration, `base_image_path`, `ssh_public_key_path` or provided public-key text, and a `vms` map. Choose *one* public-key input convention per root; load the key at the root, not inside the module. Per-VM cloud-init customization can be provided through rendered `cloudinit_data` (or a small optional map of additional user-data fields); avoid a generic templating engine or duplicate package lists across Packer/cloud-init/Ansible. Render a minimal generic user-data (ubuntu user, key, hostname, guest agent as needed), plus K3s-specific extras only in the K3s root/playbooks. Require explicit MACs for stable DHCP reservations, validate unique VM names/MACs/IPs and positive sizes, and require `disk_bytes` at least as large as the published image's virtual size (currently the Packer builder requests 20G). An environment may attach VMs to an externally owned network via its name, but must never declare that same network resource in its own state. One NIC per VM satisfies the immediate network assignment requirement; add a list of NICs only for a demonstrated multi-NIC use case.

Illustrative operator-owned example (not an assertion about the second workstation):

```hcl
vms = {
  ubuntu-01 = { hostname = "ubuntu-01", vcpu = 2, memory_mib = 2048, disk_bytes = 21474836480, mac = "52:54:00:bb:00:01", ip = "192.168.124.10" }
  ubuntu-02 = { hostname = "ubuntu-02", vcpu = 2, memory_mib = 2048, disk_bytes = 21474836480, mac = "52:54:00:bb:00:02", ip = "192.168.124.11" }
}
```

Here `ip` is a **root-level** DHCP reservation input, not a current compute-module attribute; the root projects the relevant VM fields into the compute module and passes its selected network name separately. If per-VM network assignment becomes necessary, extend the VM map with `network_name` and derive reservations by network. Provide checked-in example inputs (`*.example`), keep workstation-specific tfvars private, and document optional defaults without embedding the first workstation's path in a generic module. Output a root-owned VM-to-IP map from configured reservations for Ansible; it is declarative, **not** a runtime-discovered guest IP. If using DHCP without reservations instead, validate an alternate reachability/inventory mechanism before relying on it.

## 5. State and resource ownership

Each root has its own local `terraform.tfstate`, lock file and execution directory: `environments/k3s-lab` and `environments/ubuntu-servers`. Back up both states outside the Git checkout or to explicitly ignored, access-controlled paths. Ignore `**/.terraform/`, `**/terraform.tfstate*`, local tfvars and generated artifacts without ignoring committed `.terraform.lock.hcl`; review the new roots' lock files. Note that `terraform/terraform.tfvars` is currently **tracked**; adding an ignore rule will not untrack it. Review its actual contents locally before deciding whether to replace it with an example and remove it from tracking during implementation. A local backend is adequate for independent workstation experiments if operators serialize commands per state and back it up; it does not coordinate two different states managing the same libvirt object.

| Resource | Initial owner | Destroy contract |
| --- | --- | --- |
| Existing K3s pool `lab`, network `lab-net`, four domains, their overlays and cloud-init disks | Existing `terraform/` state, later `environments/k3s-lab` **same state** | Destroy K3s only after confirming its state and associated disks. Preserve old pool/network addresses during move. |
| Two generic Ubuntu VMs and their overlays/cloud-init disks; dedicated network and pool if chosen | `environments/ubuntu-servers` state on second workstation | Destroy only this root's owned resources. An externally supplied network/pool must not be owned here. |
| Packer base qcow2 | Operator-managed artifact outside both states | Never delete while any backing-chain overlay references it; retain old image versions through upgrades and backup/restore. |

Separate states do not alone guarantee isolation: libvirt names are host-global and shared pool/network deletion can affect a second environment. If both environments run on one host, prefer separate pools and networks. If sharing is intentional, designate one owner outside the consumer state (for example a manually precreated, documented pool/network or a dedicated infrastructure root **only if needed**), reference names as inputs, and require consumers to be destroyed or detached before retiring the owner. Avoid state outputs as a hidden cross-environment lifecycle dependency.

## 6. Packer image strategy

Keep Packer as the source of the Ubuntu 24.04 qcow2. First verify `packer build`'s actual artifact filename and boot/SSH behavior on the target workstation; the builder's current `output_directory` and `vm_name` are not the default Terraform image path. Make the existing declared Packer variables effective (`base_image_url`, pinned checksum, SSH private key), or remove redundant declarations. Ensure `create-seed.sh` and the builder use a matching, configurable key pair: the seed picks ed25519 then RSA while the builder currently fixes ed25519. Keep seed/build-only SSH access separate from guest provisioning keys; validate image cleanup (machine-id and cloud-init instance state) before cloning.

Document an explicit publication step: build → verify qcow2 format/virtual size and guest-agent/SSH behavior → copy to a host-configured base-image directory with libvirt read permission and AppArmor access → record the absolute published path in that workstation's environment input. Use versioned, immutable filenames and record checksum/provenance. Do not overwrite a base file in use by qcow2 overlays. Packer output, image publication, and Terraform plan are distinct operations; no implicit `make up` rebuild of the base image. A new image version should be tried on a new VM first, then adopted by existing VMs only with a planned disk-replacement/data-migration procedure. The existing base-image default is **not** proof that the Packer output was published there.

## 7. Ansible and cloud-init strategy

Cloud-init does day-zero guest identity/SSH access; Packer provides common image software; Ansible handles ongoing configuration. Create a generic Ubuntu playbook for the two new VMs, with an `ubuntu_base` role only if there are real repeatable tasks (e.g. packages or guest-agent service). Do not run `site.yaml` on generic Ubuntu hosts. Keep K3s server/agent playbooks, token workflow and jumpbox tooling scoped to the K3s inventory; move `k3s_version` from `all.yaml` into K3s-only vars. Retain existing K3s sysctl values in that environment until explicitly tested on rebuilt guests.

Replace the misleadingly named static `terraform.py` only after the K3s root can emit verified host/IP outputs. For the immediate two-VM deployment, a small explicit environment inventory matching the configured DHCP reservations is sufficient; alternatively generate inventory from `terraform output -json` **for the selected root**, with K3s group membership supplied explicitly by that root. Do not parse state as a substitute for declared output, assume libvirt can always report an IP, or infer K3s roles from VM names. Make SSH user/key and inventory source selectable per environment; avoid globally disabling host-key checks. Validate Ansible inventory (`ansible-inventory --list`) and reachability before any configuration run.

## 8. Workstation portability and workflows

Document on each workstation: Ubuntu 24.04 host, CPU virtualization/KVM support, qemu/libvirt and system URI access, Terraform/provider version, Packer qemu plugin, `cloud-localds`/`qemu-img`, Ansible and SSH key pair, available RAM/disk/CPU, libvirt pool parent path and writable temporary directory, pool UID/GID mapping, AppArmor policy/path access, and host network/subnet/bridge conflicts. Numeric `64055` and the checked-in AppArmor override in `etc/apparmor.d/local/abstractions/libvirt-qemu` are **specific to the original layout**; verify the host's group and adjust policy for new paths instead of copying the number blindly. Check network reachability and package repositories needed by the build and playbooks. Choose domain, MAC, IP and bridge values compatible with other host guests; compare guest disk sizing with image virtual size, not merely image file size.

For future Make targets, select a root explicitly (`ENV=k3s-lab` or `ENV=ubuntu-servers`) and run `init`, `validate`, `plan`, `apply`, `destroy`, `state-backup`, inventory/ping and the appropriate playbook in that environment. Defaulting to the existing K3s root is acceptable temporarily for compatibility, but print the resolved root/state and environment-specific destroy scope. Make `check` distinguish prerequisites for a fresh environment from existing-state/pool checks. Configure cloud-init `TMPDIR` as a host-suitable writable location only if required by the provider; verify where the provider creates and stores disks rather than assuming `TMPDIR` selects a libvirt pool. Scope `snapshot` to selected domains; currently it snapshots every running domain. Document `bin/create-vm`/`destroy-vm` as manual, unmanaged helpers and prohibit their use on state-owned domains. Preserve simple `plan → review → apply → inventory → playbook` and environment-specific `destroy` sequences.

## 9. Migration sequence with validation checkpoints

1. **Baseline the existing K3s lab (read-only).** On its workstation, record Terraform and provider versions, `terraform -chdir=terraform state list`, `terraform -chdir=terraform output`, and `terraform -chdir=terraform plan` without applying. Inspect live pool/network/domain XML, overlay backing paths, image checksum/size, DHCP leases, guest connectivity and Ansible inventory. Back up the *actual* local state and VM disks/base image before any migration. Verify the state path and resource addresses rather than assuming they match this checkout. If the plan already contains changes, explain them before migration. Do not include workstation tfvars or state in Git.
2. **Build the new generic environment independently.** Parameterize or minimally extend the compute module without renaming existing resources/instance keys. Add the Ubuntu root, two input-defined VMs, distinct pool/network if on a shared host, and minimal cloud-init/Ansible. Publish a verified Packer image on the second workstation. Validate formatting/configuration and review a plan that creates *only* the intended new root resources; validate inventories and image access. No K3s root state should be involved.
3. **Migrate the K3s root location separately.** Stop writes to the old root. Copy/move the exact current local state **and its backup** to `environments/k3s-lab` with controlled permissions (or configure that root's backend to use the exact old state path temporarily); never initialize a new empty state against existing libvirt objects. Carry over actual workstation input values without committing private tfvars. Preserve the existing root resource blocks, names, keys and module call name `compute`. Change only module and template source paths relative to the new root (for example `../../terraform/modules/compute` and `../../cloud-init/...` if using the proposed layout), then initialize the new root and compare `state list`/`plan` with the baseline. Retire the old root command path so the same objects are not managed from two state copies. This filesystem move alone should require **no** state address moves when addresses are identical; verify rather than assume a no-op plan.
4. **Change K3s inputs one dimension at a time.** Move hard-coded VM/MAC/IP/SSH values to root inputs while preserving *effective values* and map keys. Compare plans before each apply; inspect provider `ignore_changes` and live devices because a clean plan cannot detect device drift. Keep current pool/network ownership, names, base path and cloud-init contents initially. Validate `terraform output`, four leases, SSH access and K3s node health after any applied change.
5. **Optional extraction of pool/network resources.** Only if reuse warrants modules, move the **same-state** addresses using Terraform `moved` blocks or explicit `terraform state mv` after backup, e.g. `libvirt_network.lab` → `module.network.libvirt_network.this`, `libvirt_pool.lab` → `module.storage.libvirt_pool.this`; change references and validate a no-recreate plan. Exact destinations must match the implemented module names. An existing pool/network moved **between states** needs a separate planned ownership transfer (state move with `-state`/`-state-out` where supported, or remove-from-old-state then import-to-new-state), backed-up states, no concurrent operators, and plans on both sides; do **not** declare the same real object in two roots or rely on `moved` blocks across states. Avoid this transfer for the initial two-VM goal.
6. **Operational cutover.** Route Make targets and inventories to selected roots, verify `ansible-inventory --list` and K3s/site smoke checks on the original host, and generic Ubuntu SSH/guest-agent/ping plus absence of K3s services on the new host. Verify each root's plan is stable and its state lists only owned objects. Test destruction scope by *reviewing* each root's destroy plan; execute destruction only as a later, explicit operational decision.

Stop and restore from the backed-up state if a migration plan proposes unintended replacement or deletion. State-address moves do not prevent replacement caused by changed resource attributes. In particular, changing the overlay's backing path, disk capacity, domain devices/OS settings, cloud-init content/instance ID, libvirt network bridge/leases or pool path may update or replace resources, possibly destroying guest data or breaking IP/SSH/K3s connectivity; check actual provider plans. Do not change a backing image in place even if Terraform reports no changes. Copying a state to another workstation with a different libvirt daemon is **not** a portable deployment strategy: create an independent state there.

## 10. Risks and compatibility notes

* New root state under `environments/` is not covered by the current `.gitignore`; protect state, backups, tfvars and Packer seed artifacts before running a new root.
* The present `Makefile` requires pool `lab` and old `terraform.tfstate` for `up`, even when Terraform would create the pool. Do not reuse that preflight for a fresh Ubuntu environment unchanged.
* `ignore_changes = [devices]` masks useful drift (including disk/network attachment); keep it during preservation, review its provider workaround separately with live-domain checks before removing it.
* `libvirt_cloudinit_disk.commoninit` does not specify a pool, while Make sets `TMPDIR` under the lab pool. Confirm provider behavior and permissions on both workstations before claiming that an environment's cloud-init ISO is isolated by its pool.
* Packer's build SSH identity and Terraform's injected guest identity currently depend on operator home-directory defaults. Publishing an image may retain build-specific cloud-init/SSH data unless cleaned and verified; test a clone before treating it as a generic image.
* Existing static IPs are DHCP reservations, not configured guest static addresses. Inventory reachability depends on the correct libvirt network/DHCP and host routing. Existing Ansible inventory is static despite its filename.
* Historical docs describe old configurations (including absent resources and a three-VM inventory); do not use them as evidence of current running infrastructure. The exact current K3s state and provider replacement behavior remain to be established on the host before cutover.
